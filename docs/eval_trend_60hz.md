# 60Hz 冷启动线 COM3 胜率趋势分析（update 0~904）

> 只读分析，没有跑游戏，也没有改 `src/` 和 `checkpoints/`。
> 重算命令：`PYTHONPATH=src python .scratch/eval_trend.py`（加 `--md` 输出本文表格的 Markdown 版）。

## 结论

1. **update 500 以后基本平了，看不到斜率。** 主线评估胜率在 500~900 段的 logistic 斜率是 +0.012 log-odds / 100 update（SE 0.062，p = 0.84）。折算成胜率约每 100 update +0.3 pp，95% CI 为 −3.0 ~ +3.6 pp。拟合值从 60.5% 走到 61.6%。训练采样胜率给出同样的结果：500~904 段斜率 +0.014（p = 0.86）。
2. **只有把整条线（80~900）放在一起看，才有弱的正斜率。** 斜率 +0.060 / 100 update（p = 0.038），拟合值从 51.6% 到 63.5%。这个斜率来自前 500 个 update：0~399 段约 52%，400~499 段 56.5%，500 以后在 59~66% 之间摆动。从 400 开始算斜率就已经不显著（p = 0.27）。
3. **500~765 段曾出现一段上冲**（+0.216，p = 0.06；准二项修正后 p = 0.12）。它主要由几次单点高值撑起，即 705 的 80.0%、750 的 73.3%、765 的 86.7%。766~900 段立刻回落，斜率 −0.064（p = 0.84）。700~799 档 65.7% 是全线最高的一档，800~904 档回到 59.8%，两档的 CI 重叠。
4. **训练采样胜率全程没有显著趋势**（1~904 段斜率 +0.028，p = 0.22），各档在 52~64% 之间来回。它和评估胜率的走势一致。
5. **分支 D（Ticket 11 微调，从 best.pt@765 起跑，766~842）** 的评估胜率是 54.7%（82/150，CI 46.7~62.4%），训练采样胜率是 58.0%（51/88）。两者都没有超过主线 500 以后的水平。
6. **按对手角色拆分做不了。** 训练日志的 `[ep]` 行、评估行、TensorBoard 标量、checkpoint 元数据、`runs/eval/*.json` 都没有记录对手角色。`src/th155/menu.py::enter_vs_com` 的注释写的是"难度选好后按默认角色直接开打"，所以对手很可能每局都是同一个默认角色 `[INFERENCE]`。

综合来看，后半程平台在约 60%，和 §35.1 用 100 局定标 best.pt 得到的 63%（CI 53.2~71.8%）一致。继续用当前配置堆 update 数，预期得不到可检测的胜率提升。

## 方法

- **谱系（lineage）。** 看门狗多次回滚和重启，同一个 update 号会被不同进程重复跑。脚本把日志按"载入权重"切成 18 个进程段，每段的父段取"之前最近一个跑过该 update 的段"。然后从最后一个主线段（731~904）沿父指针回溯，求出每段最终被保留的 update 区间 (lo, hi]。区间外的评估和对局记作"废弃分支"。主要的废弃分支有：
  - 段 10 的 496~555 与段 11 的 552~570：看门狗在 570 熔断，回滚到 best.pt@495；
  - 段 13 的 701~705、段 14 的 706~765、段 15 的 731~735：第一次 705~765 被回滚到 best.pt@705，之后又从 ppo_000730 重启；
  - 段 7 的 281~400 没有被废弃。主线 400 实际由段 7 产出，段 8 的"载入 best.pt(280)"随即被"载入 ppo_000400"覆盖，没有跑出任何 update。
- **评估口径。** update 15/30/40 是 argmax 评估（0%），这三次不进入趋势检验。其余 56 次都是 sample 口径（20 或 30 局）。胜场数 = 胜率 × 已分胜负局数（810 那次有 1 局平局，decided=29）。
- **训练采样胜率。** `[ep]` 行用正则 `\[ep\s*\d+\]\s*(win|lose|draw)\s*\(.*?steps=\s*(\d+)` 匹配，每局归到它后面紧跟的 `[N/M]` update 行。平局不计入分母（主线共 1 局）。
- **趋势检验。** 把胜场和局数按 update 聚合成二项数据，做 logistic 回归（IRLS）。斜率单位是每 100 update 的 log-odds。同时给出 Pearson 离散度 φ，以及 φ>1 时的准二项修正 p 值。"每 100 update 胜率变化"是在均值处做的线性化近似。

## 按对手角色拆分

数据里没有对手角色。检查过的位置：

- `[ep]` 行的字段只有 result、finish、steps、life、state、ret、dmg、atk[…]、sw[…]、rw[…]；
- 评估行和 TensorBoard 的 21 个标量 tag 都不带角色；
- checkpoint 元数据、`runs/eval/*.json` 也没有角色字段；
- `configs/train_ppo_com3_60hz_coldstart.yaml` 没有角色配置；`src/th155/menu.py` 进入 VS COM 时连续按确认走默认选择。

如果需要按角色拆分，要先在环境的 episode info 里写入 P1/P2 角色 ID，再跑新的评估。

## TensorBoard 交叉校验

TensorBoard 共有 67 个 `eval/win_rate` 点，其中 59 个与日志评估逐条吻合（包括 update 15/30/40 的 argmax 0%）。其余 8 个不在这份日志里：

- update=10 100%（10 局）、update=1/2 100%（50 局）：冒烟或测试运行，不计入。
- update=770 的 43.3%、66.7%、70.0%（各 30 局），update=775 的 70.0%（50 局），update=780 的 62.0%（50 局）：10-29 晚至 10-30 从 best.pt 出发的短实验（§35 的 ref-KL、权重平均等）。它们只写进了 TensorBoard，不在 `train_60hz_coldstart.log` 里，也不属于主线。合计 120/190 = 63.2%，与平台水平一致。
- ref-KL pilot 的 update 770 为 31/50 = 62.0%，来自 `.scratch/train_refkl_pilot.log`，记在独立的 TB 目录 `runs/th155_ppo_com3_60hz_coldstart_refkl_pilot`。

与报告的交叉校验：§30 的 495 = 70.0%、570 熔断，§33 的 765 = 86.7%，§34.3 的分支 D 780/795/810 = 56.7%/63.3%/40.0%，都与日志逐条一致。
